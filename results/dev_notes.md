# Dev notes - наоди од имплементацијата (LangGraph PoC)

Суровина за Discussion секцијата на трудот. Секој запис: проблем + причина +
поправка/импликација. Хронолошки по датум на откривање.

## 1. Моделот не разбира семантичко значење на `confidence` без експлицитно објаснување

**Проблем:** intent_parser враќал `confidence: 0.0` дури и кога сите полиња биле
точно и недвосмислено извадени од барањето.

**Причина:** промптот бараше број од 0 до 1 без да дефинира што значи секоја
вредност - моделот немал основа да разликува "сигурен сум" од "не сум сигурен".

**Поправка:** прошируван prompt со експлицитна скала (1.0 = сите вредности
експлицитно наведени и нема двосмисленост; 0.5 = некои вредности недостасуваат
или се претпоставени; 0.0 = не можат воопшто да се извадат податоците). Види
`langgraph-poc/graph_v1.py::intent_parser_node`.

**Импликација:** LLM-и не третираат нумерички/скалар полиња (confidence,
score, risk 0-1) со имплицитно значење - секое такво поле бара експлицитна
дефиниција на скалата во промптот, инаку вредностите се произволни.

## 2. Structural guardrail не го фаќа игнорирањето на деловна одлука

**Проблем:** guardrail што проверува само дека JSON одговара на schema-та
("structural") пропушта случаи каде `policy_pass: false` (легитимна деловна
одлука на LLM-от) сепак резултира во продолжување на графот кон planner/dry-run.

**Причина:** JSON структурата е валидна и во двата случаи (policy_pass true
или false) - структурна проверка нема поим за "деловна" семантика на полето.

**Поправка:** секој guardrail node во графот експлицитно разликува
`structural_ok`/`guardrail_ok` (JSON schema + domain-specific semantic checks)
од `business_ok` (самата LLM одлука, пр. `policy_pass`, `is_valid`,
`overlap_found`). Двете мора да поминат за да продолжи графот. Види
`guardrail_policy_node`, `guardrail_validator_node`, `guardrail_netbox_node`.

**Импликација:** "JSON е валиден" и "одлуката е прифатена" се два независни
guardrail-и и мора експлицитно да се разликуваат во routing логиката.

## 3. qwen2.5:7b систематски тврди дека /24 е "поширок" опсег од /16

**Проблем:** моделот повторливо (2+ независни повици) го класифицирал
`10.0.5.0/24` како "поширок опсег" од /16, спротивно на вистинската CIDR
логика (поголем prefix број = потесен опсег, не поширок).

**Причина:** halucinacija / погрешна интуиција за CIDR нотацијата - моделот
изгледа ја third обратно семантиката на prefix должината.

**Поправка:** `guardrails/check_policy.py` сега независно ја пресметува
ширината преку `ipaddress.ip_network(...).prefixlen` (prefixlen < 16 = навистина
широк) и ја споредува со LLM тврдењето, независно од текстот во `violations`.

**Импликација:** силен аргумент за задолжителен semantic guardrail наспроти
чисто structural - LLM тврдења за детерминистички пресметливи факти (CIDR
аритметика, портови) никогаш не смеат да се земат здраво за готово.

## 4. qwen2.5:7b произволно класифицира порт 443 (HTTPS) како "sensitive"

**Проблем:** моделот класифицирал порт 443 како административен/чувствителен
порт и покрај експлицитно наведена листа во промптот (22, 23, 3389).

**Причина:** halucinacija на "изгледно" правило - 443 "звучи" системски/битен
порт, па моделот генерализирал надвор од дадената листа.

**Поправка:** истата семантичка проверка како во #3 - `check_policy.py`
проверува `dest_port in {22, 23, 3389}` независно и го отфрла секое
`risk_level: "high"` тврдење што не одговара на ниту еден од двата
дефинирани услови во промптот, без разлика дали LLM-от дал `violations` текст
како "образложение".

**Импликација:** дури и кога моделот дава експлицитно "образложение" во
слободен текст, тоа образложение самото по себе може да е halucinacija -
guardrail-от не смее да третира "постои образложение" како доказ дека
образложението е точно.

## 5. Conditional routing е задолжителен, не опционален

**Проблем:** со безусловни `add_edge` рути, графот "инерцијално" продолжувал
кон planner/dry_run дури и по легитимно одбивање на претходен чекор.

**Причина:** LangGraph по дифолт извршува секој следен node освен ако
експлицитно не му се каже да не продолжи.

**Поправка:** секој guardrail node проверува `state["status"]` и секој
premin меѓу чекори користи `add_conditional_edges` со `route_after_check`
(или `route_after_verify` за verify->rollback гранката), никогаш безусловен
`add_edge` меѓу два чекори каде претходниот може да отфрли.

**Импликација:** ова е централен архитектурен принцип на целиот PoC - без
условно рутирање, human-in-the-loop guardrail архитектурата е декоративна, не
функционална.

## 6. Подолги слободнотекстуални полиња произведуваат "позаконфузен" output

**Проблем:** `change_plan` и `rollback_plan` (слободен текст) произведуваат
пооделен/делумно неповрзан текст од моделот, за разлика од кратки категорични
полиња (`risk_level`, `confidence`) кои работат чисто.

**Причина:** веројатно поголем простор за halucinacija кога излезниот формат
не е строго ограничен на затворен сет вредности.

**Поправка:** `guardrails/check_planner.py` наметнува минимална должина на
`rollback_plan` (>= 10 карактери) како proxy за "не е празно/тривијално", но
не проверува семантичка точност на слободниот текст - ова е позната
ограниченост, документирана овде за Discussion.

**Импликација:** каде што е можно, полињата треба да се сведат на затворен
сет вредности (enum) наместо слободен текст - слободниот текст бара или
дополнителна LLM-базирана проверка (скапо, недетерминистичко) или се остава
неверифициран (ризик).

## 7. "Дадено образложение" не е доказ за точност - risk_level guardrail мора да биде авторитативен, не само consistency-check

**Проблем:** прв обид на semantic guardrail за policy_checker (#3/#4) го
изземаше `risk_level: "high"` тврдењето од проверка ако моделот дадеше
било каков текст во `violations` (претпоставка: "ако дал образложение,
веројатно е легитимна деловна причина надвор од двете познати правила").
Во пракса, моделот постојано тврдеше high risk за секаков input (вклучувајќи
`/32` подмрежа и порт 80, кои не ги исполнуваат ниту еден од двата дефинирани
услови) и секогаш ПРИДРУЖУВАШЕ халуцинирано "образложение" во `violations`,
па изземањето никогаш реално не важеше - guardrail-от пропуштал секое
overstated тврдење.

**Причина:** промптот експлицитно и исцрпно ги дефинира двата единствени
услови за `risk_level: "high"` ("risk_level 'high' ако ... risk_level 'high'
ако ... инаку 'low' или 'medium'"). Кога политиката е исцрпно дефинирана во
промптот, нема простор за "друга легитимна причина" - секое high тврдење
надвор од двата услови е по дефиниција неосновано, без разлика на
придружниот текст.

**Поправка:** отстранет е исклучокот "без образложение" - `check_policy.py`
сега секогаш го отфрла `risk_level: "high"` кога ниту `is_wide_subnet` ниту
`is_sensitive_port` не се точни, независно од содржината на `violations`.

**Импликација:** кога domain policy е исцрпно and затворено дефинирана во
промптот, ground-truth пресметката треба да биде АВТОРИТАТИВНА (override), не
само consistency-check против LLM-овото сопствено образложение - LLM
"образложение" за детерминистички факт не е доказ дека фактот е точен.

## 8. netbox_check е привремен mock stub

**Статус:** NetBox е недостапен на dev машината (WSL2 kernel проблем -
`wsl --update` фаќа грешка "service cannot be started", рачна инсталација на
`wsl_update_x64.msi` во тек). `netbox_check_node` (Табела 1, чекор 3) враќа
секогаш фиксен резултат `{"overlap_found": false, "existing_rules": []}` и е
јасно означен со коментар во `langgraph-poc/graph_v1.py`. Треба да се замени
со вистински API повик штом NetBox/Docker стекот е потврдено дека работи -
дотогаш, guardrail_netbox_node сепак минува низ вистинска structural
проверка (schema), само бизнис-резултатот е lažен.

## 9. Модел систематски over-flag-ира risk_level на СЕКОЈ тестиран input (вклучувајќи легитимно безбедни)

**Проблем:** во тестирање на happy-path сценарија (человек-одобрување,
apply/verify), qwen2.5:7b врати `risk_level: "high"` и за `/32` подмрежа на
порт 8080, и за `/32` подмрежа на порт 80 - двата случаи каде ниту еден од
дефинираните услови за "high" не важи. Не е откриен ниту еден пример досега
каде моделот легитимно и точно врати `risk_level: "low"` или `"medium"` за
навистина безбеден input во рачно тестирање (n=2-3 случаи).

**Причина:** веројатно системска пристрасност на моделот кон конзервативна/
"безбедна" проценка (over-caution) наместо точна семантичка проценка според
дадените правила - слично на #3/#4, но пошироко засегнато однесување, не
изолирано на еден факт.

**Импликација:** потребно е поформално тестирање (test-harness/run_experiment.py,
10x по intent) за да се измери реалната стапка на overstated vs. understated
risk_level низ поголем примерок, наместо анегдотски набљудувања. Ако стапката
на overstated grešки е висока и конзистентна, ова е самостоен наод за Results
секцијата - "моделот е систематски conservative-biased, не случајно нестабилен."

## 10. Прв целосен 10x×3-intent експериментален run (results/experiment_results.csv) - 0/30 успешни, 0 грешки/crash

**Резултати (langgraph, qwen2.5:7b, 30 вкупни pipeline извршувања):**

**Наод 1 - ниту еден run не стигна до apply/verify:** и покрај тоа што `simple`
intent-от е намерно конструиран да биде безбеден (не спаѓа во ниту еден од

деловна одлука (policy_pass=false) без наведена/детектирана причина поврзана со
дефинираните правила. Ова сугерира дека qwen2.5:7b е систематски over-cautious
дури и кога risk_level полето самото по себе е точно проценето - самата
`policy_pass` одлука изгледа е одвоено пристрасна кон одбивање, независно од
`risk_level`. Ова е важен UX/usability наод за Discussion: guardrails-ите
успешно го спречуваат halucinacija-риск (безбедносна придобивка), но моделот
исто така генерира многу false positives дури и на легитимно безбедни barawa
(usability трошок) - двете мора да се дискутираат заедно, не само едната.

**Наод 2 - `edge_incomplete` е совршено стабилен (10/10 catch rate):**
low-confidence guardrail-от (`check_intent_parser.py`) го фаќа секое нејасно
барање без исклучок и со најкратко времетраење (~5-8s, бидејќи графот
прекинува веднаш по intent_parser). Ова е најсилниот позитивен резултат од
експериментот - за овој тип на guardrail, детерминистичкиот праг (confidence
< 0.6) е целосно доволен и не бара семантичка проверка.

**Наод 3 - `policy_violating` покажува 2/10 нестабилност на validator чекорот,**
не на policy_checker (каде очекувано): истиот вход (/8 подмрежа, порт 22)
двапати резултирал во `is_valid: false` од validator-от наместо да продолжи
до policy_checker, и покрај тоа што рачно повторено тестирање со идентичен
input дало и `is_valid: true` и `is_valid: false` во различни повици (види
рачен debug тест погоре во сесијата). Ова точно одговара на очекуваната
"1-2 од 10 отстапувања" стапка од project notes, но покажува дека
нестабилноста не е ограничена на policy_checker - секој LLM чекор во
синџирот е потенцијален извор на нестабилност и му треба независен guardrail.

**Наод 4 - performance outlier: РЕШЕНО, не е модел/Docker-релевантно.**
`simple` run #4 траел 628.08s наспроти просечно ~30-40s. Истражено преку
Ollama `server.log` (`%LOCALAPPDATA%\Ollama\server.log`): пронајден е точно

per token)` - ~30x побавно од нормалната стапка на истата машина (150-230ms
по token во соседни повици). Prompt eval времето (210ms/token) е нормално,
што исклучува model-reload како причина (reload би го успорил и prompt
eval, не само decode). Windows System event log (`Microsoft-Windows-Power-
Troubleshooter`) покажува дека машината заспала во 22:29:46.737 UTC и се
разбудила во 22:39:52.758 UTC (Wake Source: Power Button) - разлика од
10m6s, речиси идентична со должината на outlier повикот. **Заклучок:
ноутбукот заспал среде-извршување на background експериментот (веројатно
Windows power-management timeout), а не Docker Desktop или resource
contention** - Docker Desktop логовите (`%LOCALAPPDATA%\Docker\log`,
`%APPDATA%\Docker\reports.log`) се stale (последна промена Jul 30/Apr 29,
нема Docker процеси активни), што го потврдува ова. Импликација за идни
експерименти: background 10x-batch тестирања на ноутбук треба да се пуштаат
со оневозможен sleep (`powercfg /change standby-timeout-ac 0` додека трае
експериментот), инаку latency-мерењата ќе содржат неточни outliers кои
немаат врска со моделот или инфраструктурата.

## 11. Одлука: retry-then-escalate НЕ е имплементиран во guardrail архитектурата

**Контекст:** првичниот архитектурен принцип (project brief) предвидуваше
"1 retry со фидбек, потоа stop + ескалирај до човек" при неуспех на
guardrail. По анализа на резултатите од #9/#10 (систематски, не случаен,
модел bias кон over-caution и halucinacija на risk_level факти), одлучено е
ДА НЕ СЕ имплементира retry логика во оваа фаза.

**Причина:** retry-then-escalate претпоставува дека неуспехот е шум (случајна
варијација) што повторен обид со истиот промпт и ист модел може да го
поправи. Емпириските наоди (#3, #4, #7, #9, #10) покажуваат спротивно -
нестабилноста е систематска пристрасност на моделот (конзистентно
misclassify-ира CIDR ширина, чувствителни портови, и over-flag-ира risk_level
дури и на легитимно безбедни barawa). Retry на истиот prompt со истиот модел
веројатно би го репродуцирал истиот погрешен резултат, трошејќи latency без
да ја подобри точноста.

**Одлука:** засега pipeline-от останува "1 guardrail failure = stop +
ескалирај до човек" (без retry чекор), додека systematic bias проблемот не
се адресира на друго ниво (подобар prompt, друг модел, или fine-tuning) - не
преку слепо повторување. Ова е документирано овде за Methodology/Limitations
секцијата на трудот, како свесна архитектурна одлука базирана на податоци,
не пропуст.

**Заклучок (ажурирано):** 0/30 crash/error исходи во првиот експериментален
run - pipeline-от е робустен и conditional routing-от го прекинува
извршувањето точно каде треба во сите случаи. Бидејќи ниту еден од 3-те
првобитни тест intents не стигна до human approval/apply/verify чекорите
во автоматизирано тестирање, додаден е 4ти intent (`guaranteed_safe` -
host-to-host /32, порт 9090, надвор од секој дефиниран "high risk" услов)
специфично дизајниран да го измери реалниот success rate на целиот pipeline
(вклучувајќи human approval/apply/verify) статистички - резултати подолу.

## 12. `guaranteed_safe` intent (4ти test intent, 10 runs) - потврдува Наод 9: 0/10 успешни

**Резултати:** 3/10 `rejected_at_policy_checker_guardrail` (halucinirano
"high" risk, фатено од semantic guardrail); 7/10 `rejected_at_policy_checker_denied`
(policy_pass=false БЕЗ прекршување на дефинираните правила - risk_level

**Комбиниран резултат низ двата НАМЕРНО безбедни intents (`simple` + `guaranteed_safe`,
две независни формулации, вкупно 20 повторувања):** 0/20 успешни. 7/20
(35%) halucinirani high-risk тврдења (фатени од guardrail), 13/20 (65%) чисти
деловни одбивања без прекршување на дефинираните правила. **Ниту еден
единствен run во целиот експеримент (n=40 вкупно, вклучувајќи ги и
`policy_violating` и `edge_incomplete`) не поминал низ policy_checker со

независно од вистинската безбедносна проценка. Ова е самостоен, силен наод
за Results/Discussion секцијата: guardrail архитектурата успешно ја
компензира halucinacija-компонентата (35% од одбивањата се фатени и означени
како неоснователни), но не може да ја компензира business-decision
пристрасноста (65%) - за тоа е потребна промена на promptот/моделот, не
guardrail на JSON исход. Human-in-the-loop чекорот (apply/verify/rollback)
останува целосно потврден само преку изолирано/рачно тестирање во оваа
сесија, не преку автоматизиран pipeline run - идна работа: или ре-дизајн
на policy_checker промптот (пр. експлицитно "default to policy_pass:true
ако ниту еден услов не е исполнет"), или прифаќање дека 0% autonomous
success rate самиот по себе е валиден резултат за трудот (поддржува
централната теза - human-in-the-loop е неопходен, не опционален).

## 13. Контролиран експеримент: изменет policy_checker промпт (v2) - делумно, не целосно, го поправа Наод 12

**Setup:** `langgraph-poc/experiment_policy_v2.py` (привремен фајл, НЕ ги
менува `graph_v1.py` ниту `check_policy.py`) дефинира `policy_checker_node_v2`
со додаден експлицитен ред во промптот: *"Ако правилото НЕ го исполнува ниту
еден од двата дефинирани high-risk услови, задолжително policy_pass: true и
risk_level: 'low'."* Сите останати nodes/guardrails се идентични (реупотребени
директно од `graph_v1`). 10 повторувања на `guaranteed_safe` intent-от,
логирани во `results/experiment_results.csv` со `platform=langgraph_prompt_v2`
за да се разликуваат од оригиналната серија (`platform=langgraph`).

**Резултати (v2) наспроти оригиналот (v1, Наод 12), ист `guaranteed_safe` intent:**

| исход | v1 (оригинален промпт) | v2 (експлицитен default-true) |
|---|---|---|
| поминал policy_checker (policy_pass: true) | 0/10 | **2/10** |
| `rejected_at_policy_checker_guardrail` (halucinirano "high") | 3/10 | 4/10 |
| `rejected_at_policy_checker_denied` (business denial) | 7/10 | 4/10 |
| стигнал до целосен success (`ok`, apply/verify) | 0/10 | 0/10 (двата runs што поминаа policy_checker паднаа подоцна на `planner`, види подолу) |

**Наод 1 - експлицитната инструкција помага, но не го решава проблемот:**
policy_checker pass-through стапката се подобри од 0% на 20% (2/10) - реална,
мерлива промена, не шум (n=10 премалку за силна статистичка тврдба, но
насоката е јасна и во согласност со прогноза). Сепак, стапката на
halucinirani "high risk" тврдења НЕ се намали (3/10 -> 4/10, во рамките на
шум за n=10) - експлицитната default-true инструкција не спречува halucinacija
на самите CIDR/port факти, само го намалува чистото business-denial без
образложение. Ова сугерира дека прашањето не е еднородно: делот од
пристрасноста доаѓа од "конзервативен default" (поправливо со prompt) додека
делот доаѓа од факtualна halucinacija (CIDR/порт погрешна проценка,
непроменето со овој prompt fix).

**Наод 2 - нов bottleneck откриен на planner чекорот (2/10 runs):** двата
runs што првпат поминаа policy_checker (run 4 и 8) паднаа веднаш потоа на
planner - моделот вратил `change_plan` како структуриран JSON низа од чекори
(`[{"step":1,"action":"...","details":"..."}, ...]`) наместо plain string,
прекршувајќи го `planner.schema.json` (`change_plan: {"type": "string"}`).
Guardrail-от (`check_planner.py`, jsonschema validation) го фатил ова коректно
(`rejected_at_planner`, structural error). Ова е првиот пат во целата серија
експерименти каде planner чекорот реално блокира извршување (претходно
секогаш policy_checker блокираше прв) - в склад со Наод #6 (подолги
слободнотекстуални полиња произведуваат понепредвидлив output), но сега
емпириски потврдено како реален blocking failure mode, не само "confusing
text". Двата runs со ова однесување биле и најбавни (135.99s и 104.84s
наспроти ~22-49s за останатите) - веројатно затоа што генерирање на
структурирана JSON низа со повеќе полиња бара значително повеќе tokens од
кратка реченица, не аномалија/sleep (за разлика од Наод #4).

**Заклучок:** ниту v1 ниту v2 промптот не постигна ниту еден целосен success
(`ok`) во автоматизирано тестирање - но v2 покажа дека prompt-level
интервенции ДЕЛУМНО помагаат (0%→20% policy_checker pass-through) без да го
решат проблемот целосно, и дека решавање на еден bottleneck (policy_checker
over-caution) веднаш го открива следниот (planner schema non-compliance).
Ова е силен аргумент за Discussion: guardrails/human-in-the-loop архитектурата
не е привремена мерка додека промптите се "дотерани" - секој chain од
детерминистички недоверливи LLM чекори ќе продолжи да бара guardrail на
секое ниво, независно колку се подобрува секој поединечен промпт.
Оригиналниот `graph_v1.py` и `run_experiment.py` НЕ се менувани во текот
на овој контролиран експеримент - `experiment_policy_v2.py` и
`run_experiment_v2.py` се привремени и може да се избришат откако наодот
е документиран (веќе е, овде).

## 14. Model-agnostic рефактор - подготовка за multi-model споредба (пред n8n)

**Зошто:** менторката најави дека наскоро добиваме пристап до поголеми LLM-ови
(Llama3.3, Qwen, DeepSeek, GLM, gpt-oss) преку надворешен API, како
замена/дополнение на локалниот `qwen2.5:7b`. Архитектурата требаше да
дозволува замена на модел/провајдер без рачно менување на секој prompt повик.

**Што е направено:**
- Нов `guardrails/llm_client.py` - единствено место со `MODEL_NAME` (читано
  од `LLM_MODEL` env var, fallback `qwen2.5:7b`) и `LLM_PROVIDER` (`ollama`
  default, `external` подготвено но фрла `NotImplementedError` со јасна
  порака додека не добиеме endpoint/token од менторката). `call_llm(prompt)
  -> str` е единствената точка на влез - internally одлучува Ollama vs
  надворешен API, го форсира JSON output mode, го враќа суровиот текст
  (повикувачот сепак прави `safe_json_parse()`).
- Сите 4 повици во `langgraph-poc/graph_v1.py` (intent_parser, validator,
  policy_checker, planner) сега користат `call_llm()` наместо директен
  `ollama.chat(model="qwen2.5:7b", ...)`.
- `langgraph-poc/experiment_policy_v2.py` (контролираниот експеримент,
  Наод #13) исто ажуриран за конзистентност - инаку ќе останеше единствениот
  node hardcoded на "qwen2.5:7b" додека сите останати nodes веќе го читаат
  MODEL_NAME, што ќе создадеше тивка неусогласеност при идно тестирање со
  друг модел.
- `test-harness/run_experiment.py` и `run_experiment_v2.py` - додадена
  `"model"` колона во CSV_FIELDS, пополнета од `MODEL_NAME` во моментот на
  извршување. Постојниот `results/experiment_results.csv` (50 редови од
  експериментите #10, #12, #13) е мигриран - додадена `model=qwen2.5:7b`
  колона на сите постоечки редови (точна историска вредност, потврдена преку
  сите претходни smoke тестови и Ollama логови во оваа сесија), не изгубени
  податоци.

**Верификација:** brz smoke test по рефакторот (`guaranteed_safe` intent)
даде идентичен образец на однесување како пред рефакторот - guardrail
коректно фати уште еден halucinirani "high risk" claim
(`risk_level_overstated_hallucinated` за /32 subnet + порт 9090), потврдувајќи
дека рефакторот не влијае на pipeline логиката, само на конфигурацијата.
Дополнително проверено: `LLM_PROVIDER=external` чисто фрла `NotImplementedError`
со објаснување, `LLM_PROVIDER=<непознато>` фрла `ValueError` - двете
fail-fast, не тивко fallback на погрешно однесување.

**Импликација:** идно тестирање со надворешни модели (кога го добиеме API
пристапот) ќе бара само `_call_external()` да се имплементира еднаш во
`guardrails/llm_client.py` плус `LLM_MODEL=<модел>` и `LLM_PROVIDER=external`
env variables - нула промени во node промптите или графот. `platform` колоната
во CSV останува orthogonal димензија (langgraph/n8n/langflow) - `model`
дозволува независна споредба на модели В рамки на иста platform.

## 15. n8n Ollama Chat Model credential не се поврзува преку "localhost" - IPv6-first DNS resolution во Node.js

**Проблем:** При поставување на "Ollama Chat Model" sub-node во n8n (за AI
Agent vs Chain експериментот), credential тестот со Base URL
`http://localhost:11434` враќал "Couldn't connect with these settings" /
"The service refused the connection - perhaps it is offline", и покрај тоа
што Ollama е потврдено достапен на истата адреса преку `curl` од Python/Bash
страна во истиот момент (200 OK, `qwen2.5:7b` во листата).

**Причина:** Node.js (в. 17+, а тука конкретно v24.16.0) по default ја
преферира IPv6 резолуција за "localhost" (враќа `::1` пред `127.0.0.1`).
Ollama на Windows слуша стандардно само на `127.0.0.1` (IPv4), не и на `::1`
- па Node-based n8n процесот се обидува да се поврзе на IPv6 loopback каде
никој не слуша, добива "connection refused", додека алатки надвор од Node
(curl, requests од Python) не го погодуваат истиот проблем бидејќи по default
резолвираат "localhost" поинаку или прво пробуваат IPv4.

**Поправка:** Base URL во credential-от експлицитно сменет на
`http://127.0.0.1:11434` (IPv4 адреса наместо hostname) - connection тестот
веднаш поминал по оваа промена.

**Дополнителна компликација (истиот root cause):** дури и по успешно
зачувување на credential-от, "Model" dropdown полето продолжило да прикажува
"Error fetching options from Ollama Chat Model" (со заведувачки hardcoded
placeholder "llama3.2" во manual-entry режим - модел кој воопшто не е
инсталиран локално). Ова се решило со експлицитен "Refresh List" преку "⋮"
менито до полето (не автоматско по credential save) - потоа dropdown-от
коректно го прикажал вистинскиот инсталиран модел "qwen2.5:7b".

**Импликација:** секој иден n8n node што се поврзува на локален сервис преку
"localhost" (не само Ollama) на оваа Windows машина треба експлицитно да
користи `127.0.0.1` наместо "localhost" во конфигурацијата - ова е платформо-
специфичен gotcha (Node.js DNS resolution поведение), не n8n-специфичен бug,
и веројатно ќе влијае и на HTTP Request nodes кон `guardrail_api.py` (port
9100) и mock firewall (port 9000) подоцна во pipeline изградбата - треба
однапред да се користи `127.0.0.1` во сите n8n node конфигурации кон локални
сервиси, не "localhost".

## 18. n8n validator чекор: моделот врати markdown-wrapped JSON + вишок проза - LangGraph немаше овој проблем

**Setup:** проширен истиот workflow со validator чекор по образецот на
`graph_v1.py::validator_node` - нов "Basic LLM Chain1" node поврзан на IF
(true) излезот од intent_parser guardrail проверката, промпт со expressions
кои читаат назад до првиот "Basic LLM Chain" node (`{{
JSON.parse($('Basic LLM Chain').item.json.text).source_subnet }}` итн.,
потврдено дека точно се резолвираат до "Правило: 10.0.5.0/24 ->
10.0.10.15:443/tcp" преку live preview пред извршување). Ollama Chat
Model2 sub-node, Model рачно сменето од default `llama3.2` на `qwen2.5:7b`
(истиот gotcha како во Наод #17, повторен по трет пат - потврдува дека ова
е доследно, не еднократно однесување на n8n).

**Резултат:** извршувањето успеа (сите nodes зелено), НО излезот од
Ollama Chat Model2 (`.text` полето на Basic LLM Chain1) не е чист JSON:

```
```json\n{"is_valid": true, "errors": []}\n```\n\n### Објаснување:\n- *...
(проследено со целосно markdown-форматирано образложение на македонски -
наслови, bold текст, bullet points)
```

Самата JSON содржина е точна (`is_valid: true, errors: []`, коректно за
валидно правило), но е обвиткана во ```` ```json ... ``` ```` fence И
проследена со дополнителна проза по затворената fence - за разлика од
intent_parser чекорот (Наод #16/#17) кој и во AI Agent и во Basic LLM
Chain верзија секогаш враќаше чист, непроширен JSON низ сите 15+
извршувања досега.

**Причина (хипотеза, потребна е потврда):** `graph_v1.py::call_llm()`
експлицитно испраќа `format="json"` до Ollama API (принудува constrained
JSON generation мод, забранувајќи \i markdown fences и прозен текст). n8n
"Ollama Chat Model" LangChain node-от има checkbox "Require Specific
Output Format" во Basic LLM Chain параметрите (default: ИСКЛУЧЕНО) - ова
веројатно е n8n-еквивалентот на `format="json"`, но не е активиран во
досегашната конфигурација. Ако ова е точно, разликата НЕ е случајна LLM
нестабилност туку конфигурациска разлика помеѓу платформите - LangGraph
секогаш принудува JSON мод, n8n Basic LLM Chain default не го прави тоа.

**Импликација - методолошки критично:** ова значи дека `guardrails/common.py::safe_json_parse()`
(со `strip_markdown_fences`) НЕ е доволен за овој случај - regex-от бара
стрингот да ЗАВРШУВА со ```` ``` ````, но овде има проза ПОСЛЕ затворената
fence, па дури и Python-ската верзија би паднала на овој конкретен
пример. n8n HTTP Request-от кон `guardrail_api.py` со наивен `{{
JSON.parse($json.text) }}` expression ќе фрли грешка на овој output (не е
валиден JSON стринг во целост). Пред да се додаде HTTP Request за validator
guardrail проверка, ПРВО треба да се реши ова.

**Одлука и решение:** испробани се двете опции.
"Require Specific Output Format" (опција а) е одбиена - n8n бара поврзан
"Output Parser" sub-node со сопствен JSON schema, што ќе значеше
дуплирање на schema дефиниции кои веќе постојат во `contracts/*.schema.json`
(спротивно на "не преизмислувај ја guardrail логиката во n8n" принципот).
Наместо тоа, применето е решение (б) на ДВЕ места за конзистентност:

1. `guardrails/common.py::strip_markdown_fences()` - regex променет од
   anchored (`^```...```$`, бараше fence-от да е ЦЕЛИОТ стринг) на
   non-anchored (`re.search` наместо `re.match`, наоѓа fence БИЛО КАДЕ во
   текстот). Потврдено со 3 тест случаи: чист JSON, fenced JSON без вишок,
   и fenced JSON + proza по затворената fence (новиот случај) - сите
   поминуваат, `test-harness/test_guardrails.py` сепак поминува непроменето.
2. n8n HTTP Request "JSON" полето за validator guardrail проверка користи
   аналогна non-anchored JS екстракција наместо гол `JSON.parse($json.text)`:
   `{{ (() => { const t = $json.text; const m = t.match(/\`\`\`(?:json)?\s*([\s\S]*?)\`\`\`/); return JSON.parse(m ? m[1] : t); })() }}`

**Импликација:** овој наод директно ја подобри Python guardrail логиката
(не само n8n side) - да не беше откриено преку n8n тестирањето, истиот gap
ќе останеше неоткриен во LangGraph, бидејќи intent_parser/policy_checker
тестовите досега случајно не наишле на "проза по fence" примерок од
qwen2.5:7b. Вреден пример за методолошка корист од тестирање на иста
логика низ повеќе платформи - различните orchestration слоеви ги
провоцираат различните LLM однесувања/edge cases.
