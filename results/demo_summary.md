# Demo summary —


---

## 1. Кратко резиме 

**LangGraph — комплетно.** Сите 10 чекори од Табела 1 имплементирани и тестирани: intent parsing → validation → NetBox check → policy check → planning → dry-run → **човечко одобрување** → apply → verify → **условен rollback**. Секој чекор има guardrail што проверува дали LLM-одговорот е структурно и семантички точен пред да продолжи. Спроведен е и статистички експеримент (40 извршувања низ 4 тест-сценарија) за да се измери реалната стапка на успех, не анегдотски.

**n8n — комплетно.** Истите 10 чекори, истата споделена guardrail логика (`guardrails/*.py` — LangGraph ја повикува директно, n8n преку HTTP wrapper), реимплементирани во n8n workflow-от. Секој чекор поединечно тестиран и потврден, вклучувајќи го најделикатниот дел — паузирање на извршувањето и чекање на човечко Approve/Deny преку веб-форма, и автоматски rollback ако верификацијата по примена на правилото открие несовпаѓање.

**Langflow — не почнато.** Празен placeholder директориум. Следна платформа на ред откако денес/утре завршуваме со n8n демото.

## 2. Клучни 3-4 наоди што ја поддржуваат централната теза (human-in-the-loop е неопходен)

**Наод 1 — 0 од 40 автономни извршувања успеале, дури и за легитимно безбедни барања.**
Два различни "безбедни" тест-intent-а (`simple`, `guaranteed_safe`), 20 повторувања секој = 40 вкупно. Ниту еден единствен пат моделот не поминал низ policy-проверката со точна, автономна одлука. 35% од одбивањата се halucinirani "high risk" тврдења (фатени од guardrail-от); 65% се чисти деловни одбивања без прекршување на кое било дефинирано правило. **Ова е директен доказ дека guardrails сами по себе не се доволни — некој МОРА да го гледа секој случај.**

**Наод 2 — семантички guardrails фаќаат нешто што структурните не можат.**
Модел тврди "risk_level: high" и дава образложение што "звучи" убедливо. Guardrail-от независно ја пресметува вистината (CIDR ширина, дали портот е навистина чувствителен) и го отфрла тврдењето кога не се совпаѓа — независно од тоа колку убедливо звучи образложението на моделот. Чиста JSON-schema проверка (структурна) ова НЕ би го фатила.

**Наод 3 — подобар prompt делумно помага, но не го решава проблемот.**
Контролиран експеримент со експлицитно подобрен prompt: policy pass-through стапка се подобри од 0% на 20% — реална промена, но веднаш откри НОВ проблем (planner-от почна да враќа погрешно форматиран JSON). **Решавање на едно тесно грло веднаш го открива следното** — доказ дека guardrail архитектурата не е привремена закрпа додека се "дотерува" промптот, туку структурна потреба.

**Наод 4 — rollback механизмот работи, потврдено и во LangGraph и во n8n со истата споделена логика.**
Кога verification-от по примена на правило открие несовпаѓање, автоматскиот rollback навистина се извршува — потврдено не само преку guardrail-овиот извештај, туку преку директна проверка на реалната состојба на firewall-от (правилото навистина е избришано). Истата Python `check_verifier` логика работи идентично на двете платформи.

**Заклучок:** guardrails ја фаќаат halucinacija-та (35% од случаите), но НЕ можат сами да ја поправат системската conservative-bias деловна одлука (65%) — тоа бара или подобар модел/prompt (идна работа, надворешен API пристап), или — засега, единствено докажано решение — човек во јамката.

## 3. Демо скрипта — точен редослед

### Дел А — LangGraph во живо (безбедно, брзо)

1. ** `edge_incomplete` intent во живо** 
   - 100% стабилно (10/10 во експериментот), **5-8 секунди**, нула ризик.
   - Покажува: guardrail го фаќа нејасното барање веднаш на intent_parser, пред да продолжи понатаму.
   - Команда (од project root, со активиран venv): `python langgraph-poc/demo_run.py edge_incomplete`
   - *Забелешка:* `graph_v1.py::__main__` има hardcoded raw_request (не прифаќа CLI влез), затоа е направен мал helper `langgraph-poc/demo_run.py` кој го пушта истиот `run_pipeline()` со кој било од 4-те тест-intent-и без да се допира `graph_v1.py`. Веќе тестиран и потврден (Дел 4, Чекор 5).

2. **policy_violating` intent во живо** (навистина широк /8 опсег + порт 22).
   - Стабилно (8/10 во ~20-50s, останатите 2/10 паѓаат на validator — сепак guardrail-catch, не пад).
   - Покажува: policy guardrail коректно го препознава ГЕНУИНО лошото правило (не halucinacija — вистинско прекршување).
   - Команда: `python langgraph-poc/demo_run.py policy_violating`

3. **НЕ пуштај `guaranteed_safe` во живо.** Наместо тоа, цитирај ги бројките од Дел 2 погоре (0/40) — тоа е посилен доказ од еден анегдотски run, и нема ризик да заглави подолго од очекувано.

**Времетраење на Дел А:** ~1-2 минути ако само edge_incomplete, ~2-3 минути со policy_violating.

### Дел Б — n8n canvas + подготвени executions (безбедно, визуелно impresivno)

1. **Прикажи го целиот n8n canvas** (Editor таб, zoom-to-fit) — сите чекори видливи одеднаш. Спомени: истата 10-чекорна логика бара значително повеќе индивидуални n8n nodes (~30+) отколку LangGraph-овите 10 graph nodes — самото ова е talking point за code-first наспроти low-code компромисите.

2. **Отвори ја веќе-завршената execution #47 (success патека)** — Executions таб → кликни на извршувањето од `23:35:47` → Logs панел → Details таб. Прошетај низ неколку чекори (особено If8 → True Branch, Pipeline Success). Нула ризик, веќе завршено.

3. **Отвори ја веќе-завршената execution #48 (rollback патека)** — Executions таб, првиот/најнов запис (`23:47:50`). Прошетај до If8 (False Branch, `field_mismatch:dest_port`), HTTP Request9 (`rolled_back:true`), If9 (True Branch). Ова е "wow" моментот — покажи дека rollback навистина работи.

4. **(По желба, bonus ако има доверба/време) Жив run со реално Approve.**
   - Кликни "Execute workflow", остави го да работи (~1-2 минути реални LLM повици).
   - Кога стигне до Wait, ќе се отвори форма во browser-от — кликни "approve" НОРМАЛНО (важно: ова работи глатко во твојот вистински browser; проблемот со блокирано поднесување на форма што го најдов при тестирање е специфичен САМО за автоматизираниот sandboxed browser alatka што јас го користев за тестирање, не постои во нормален Chrome/Edge).
   - Ризик: real LLM повици можат случајно да paднат на policy_checker guardrail пред да стигнат до Wait (истата model bias од Дел 2) — ако сакаш 100% гарантирано да стигнеш до Wait, прескокни го ова и остани на веќе-снимените executions.

**Времетраење на Дел Б:** ~3-5 минути со само #47/#48, +2-3 минути ако додадеш жив run.

### Дел В — Langflow

Само вербално: "не почнато, следно на ред." Нема демо — нема што да се покаже.

**Вкупно времетраење на целото демо:** ~6-10 минути технички дел + колку сакаш за прашања.

## 5. Веројатни прашања од менторката + кратки одговори

**„Зошто qwen2.5:7b, не поголем модел?“**
Локален, бесплатен, доволно мал за да работи на лаптоп без GPU-cloud трошок — добар за PoC фаза. `guardrails/llm_client.py` веќе е подготвен (model-agnostic рефактор) за multi-model споредба штом добиеме пристап до поголеми модели (Llama3.3, DeepSeek, GLM, gpt-oss) преку надворешен API.

**„Дали резултатите ќе се сменат со подобар модел?“**
Веројатно да за halucinacija-компонентата (35% од одбивањата — погрешни CIDR/port тврдења, поголем модел веројатно е попрецизен). Но 65-те% чисти деловни одбивања изгледаат како conservative prompt-level bias, не нужно поврзано со големина на моделот — ова е токму прашањето на идниот multi-model експеримент, не претпоставка.

**„Колку време ти треба за Langflow?“**
Најтешкиот дел (guardrail логика, промптови, тест-intents) е веќе готов и повторно употреблив — само orchestration слојот се менува. n8n делот (сите 10 чекори, вклучувајќи го Wait/Form механизмот и rollback) заврши за неколку работни сесии. Очекувам Langflow да биде во слично темпо или малку побрзо — генералниот пристап ("секој чекор = HTTP повик + guardrail + conditional routing") е веќе докажан образец од n8n; единствениот непознат фактор се Langflow-специфичните platform quirks (аналогни на n8n-овите pin-data/expression-режим изненадувања), кои не можат да се предвидат однапред, само откријат при работа.

**„Дали rollback патеката е робустна?“**
Да — тестирана end-to-end со реални (не-мокирани) HTTP повици, и потврдена не само преку guardrail-овиот извештај туку преку директна проверка на вистинската состојба на mock firewall-от (правилото навистина е избришано). Единствената нијанса: за да се симулира реален mismatch за тестирање, морав намерно да внесам погрешна вредност во apply-повикот (реалните apply-и речиси никогаш сами не создаваат несовпаѓање) — но самиот detection+rollback механизам е целосно докажан со реални повици.

**„Дали е фер споредбата меѓу платформите?“**
Да — истата Python guardrail логика (`guardrails/*.py`) се користи директно (in-process) од LangGraph и преку HTTP wrapper од n8n. Ниту еден ред guardrail логика не е реимплементиран по платформа — разликите што ги мериме се чисто за orchestration-слојот, не за квалитетот на guardrails.

**„Што е следен чекор по Langflow?“**
1. Langflow имплементација (истите 10 чекори).
2. 10x-repetition статистички test-harness за n8n (истата методологија како LangGraph-овиот `run_experiment.py`), за директна платформена споредба со бројки, не анегдоти.
3. Multi-model споредба штом добиеме надворешен API пристап до поголемите модели.

**„Зошто n8n имаше толку многу технички проблеми/наоди?“**
Токму тоа Е самиот наод — n8n-от, како low-code платформа, има своја категорија ризици кои code-first платформата (LangGraph) ги нема: тивки конфигурациски грешки (localhost наспроти 127.0.0.1, Fixed наспроти Expression режим по поле, pin-data кое не се почитува доследно по Wait-чекор) — грешки што НЕ фрлаат exception, туку тивко пренесуваат погрешни податоци. Ова е директно Discussion-секција материјал за trade-offs меѓу code-first и low-code orchestration.
